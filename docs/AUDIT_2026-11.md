## 2. Constats, par priorité

### 🔴 Critique — bloque la promesse « preuve de sinistre » et la migration OVHcloud

**C1. Le serveur souverain est un prototype en mémoire.**
`sovereign-core/server/index.js` stocke utilisateurs, points et sessions dans des `Map` JavaScript. PostgreSQL (`db/schema.sql`) n'est jamais utilisé (`pg` n'est jamais `require`). Un redémarrage efface tous les comptes. Il n'y a ni WebSockets ni routes « hazards », contrairement à ce que dit `CLAUDE.md`.

**C2. La signature ECDSA de la boîte noire ne prouve rien côté serveur.**
`/api/v1/telemetry/upload` vérifie la signature avec la **clé publique envoyée par le client** (`ecdsaPublicKey`) et accepte un `hardwareId` libre. N'importe qui peut signer de fausses données avec sa propre clé et obtenir `ecdsaVerified: true`. Il faut comparer avec la clé enregistrée pour ce boîtier au provisionnement (`functions/api/blackbox-registry.js` existe déjà mais n'est pas branché).

**C3. Le chiffrement « E2EE » côté navigateur utilise une clé devinable.**
`src/js/blackbox.js:115` chiffre avec `"BB_SENTINEL_" + uid`, et `src/js/wallet.js:21` avec `"QUANTUM_" + deviceId + uid`. Ces clés se reconstruisent à partir de données connues : ce n'est pas du chiffrement de bout en bout. De plus, `crypto-js` n'est plus maintenu.

### 🟠 Élevé

**E1. Pas de CSP sur le domaine principal.** `mon50ccetmoi.com` est servi par GitHub Pages, qui ignore les en-têtes de `firebase.json`. La CSP, HSTS, etc. ne s'appliquent donc qu'à `mon50ccetmoi.web.app`. Aucune balise `<meta http-equiv="Content-Security-Policy">` dans les pages.

**E2. Règles Firestore : créations sans validation.** ~14 collections (`hazards`, `insurer_reports`, `emergency_alerts`, `crash_reports`…) acceptent `allow create: if isSignedIn()` sans contrôle du contenu. Exemple : dans `hazards`, un utilisateur peut écrire n'importe quel champ `author`, donc se faire passer pour un autre puis modifier ce document.

**E3. Clé JWT éphémère.** `crypto-auth.js` génère une nouvelle paire de clés à chaque démarrage si `SOVEREIGN_JWT_PRIVATE_KEY` est absent : tous les utilisateurs sont déconnectés à chaque redémarrage, et plusieurs instances ne se comprennent pas. En production, le serveur doit refuser de démarrer sans clé.

**E4. Pas de limitation de débit sur `/auth/login`** (attaque par force brute possible).

**E5. Firmware : Secure Boot et chiffrement Flash désactivés** (`sdkconfig.defaults`, lignes 20-29 commentées) ; JTAG actif. Pour un boîtier vendu comme preuve juridique, c'est indispensable avant la production.

### 🟡 Moyen

- **M1.** `tamper_zeroize()` est marqué `IRAM_ATTR` alors qu'il efface la Flash. Il est bien appelé hors ISR (`main.c:179`), mais l'étiquette est trompeuse. Il est aussi rappelé à chaque tour de boucle tant que l'état n'est pas « SAFE ».
- **M2.** Documentation incohérente : `CLAUDE.md` parle d'AES-256-**CBC**, le code utilise AES-256-**GCM** (ce qui est mieux) ; WebSockets/PostGIS annoncés mais absents.
- **M3.** RGPD : `DELETE /rgpd/account` ne supprime pas les `telemetrySessions` ni ne documente la conservation des preuves WORM (base légale à écrire).
- **M4.** `innerHTML` utilisé ~150 fois (protégé par DOMPurify via `dom-security.js`) et `onclick=` inline dans ~20 pages HTML, ce qui empêchera une CSP stricte.
- **M5.** Clés Google (`src/js/config.js`) dans le code : normal pour des clés navigateur, **à condition** qu'elles soient restreintes par domaine dans la console Google Cloud (à vérifier).

## 3. Plan d'implémentation

Chaque phase est indépendante et se termine par `npm test` + `npm run lint` + `npm run build` au vert.

### Phase 0 — Filet de sécurité (½ journée)
1. Ajouter un workflow CI `test.yml` : `npm ci`, `npm run lint`, `npm test`, `npm run build` sur chaque push/PR.
2. `npm audit fix` (minimatch).
3. Corriger `CLAUDE.md` (GCM, état réel de `sovereign-core`).

### Phase 1 — Correctifs de sécurité immédiats (2-3 jours)
1. **C2** : registre des boîtiers côté serveur. La clé publique ECDSA est enregistrée au provisionnement ; l'upload vérifie la signature contre cette clé et rejette un `hardwareId` inconnu ou non lié à l'utilisateur. Tests à l'appui.
2. **E3** : refuser le démarrage en `NODE_ENV=production` sans clés JWT ; script `generate-keys`.
3. **E4** : limitation de débit sur login/register (par IP + par email).
4. **E2** : règles Firestore — imposer `request.resource.data.author == getUsername()` (et équivalents), limiter les champs avec `keys().hasOnly([...])` et tailles max ; étendre `firestore.rules.test.js`.
5. **E1** : ajouter une CSP en `<meta>` dans chaque page (ou basculer le domaine sur Firebase Hosting / OVH qui servent les en-têtes).

### Phase 2 — Vraie boîte noire côté navigateur (2 jours)
1. **C3** : remplacer `crypto-js` par WebCrypto (`AES-GCM`, clé non extractible stockée dans IndexedDB, ou chiffrement par la clé publique du serveur). Supprimer `crypto-js.min.js`.
2. Migration des données déjà chiffrées dans `wallet.js` (déchiffrer avec l'ancienne clé, rechiffrer).

### Phase 3 — Rendre `sovereign-core` réel (1-2 semaines) = Phase A de la roadmap
1. Couche d'accès PostgreSQL (`pg` Pool) pour users / points / sessions / blackbox_units à la place des `Map`.
2. Routes manquantes : hazards (PostGIS, recherche par rayon), profils, points.
3. Corriger `docker-compose.yml` : image construite avec `npm ci` (Dockerfile), healthcheck API, Redis réellement utilisé ou retiré.
4. Tests d'intégration contre un Postgres de test.
5. Brancher le frontend via `CONFIG.BACKEND_MODE = "FIREBASE" | "SOVEREIGN"` (auth, database, blackbox-ble), Firebase restant par défaut.

### Phase 4 — Firmware production (avant toute vente de boîtier)
1. **E5** : activer Secure Boot v2 + Flash Encryption (mode release) + désactiver JTAG, documenter la procédure de provisionnement usine.
2. **M1** : retirer `IRAM_ATTR` de `tamper_zeroize()`, n'exécuter l'effacement qu'une fois.
3. Compiler en CI (`idf.py build`) dans un conteneur ESP-IDF.

### Phase 5 — Nettoyage et performance (en continu)
1. Retirer `dist/` du dépôt (déjà généré par la CI) ; sortir les zip/aab du dépôt.
2. Choisir une seule voie Android (Capacitor *ou* TWA) et supprimer l'autre.
3. Découper le bundle `app` (import dynamique de la carte, du copilote, des modules rares) ; charger Firebase à la demande.
4. Remplacer progressivement les `onclick=` par `data-action` pour permettre une CSP sans `unsafe-inline`.

### Phase 6 — OVHcloud (Phases B et C de la roadmap)
Copilote Mistral via OVHcloud AI Endpoints, puis déploiement GRA/RBX une fois la Phase 3 terminée.
